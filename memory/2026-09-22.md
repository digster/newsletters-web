# 2026-09-22 — Email links open in a new tab

## Problem

In the viewer, clicking a link in an email (e.g. the headline, to read the post on the
publisher's site) tried to load inside the iframe and failed.

## Root cause

`view.html` sandboxed the email iframe with only `allow-same-origin`:

- Links without a target navigated the iframe itself. Publishers send
  `X-Frame-Options: DENY` / CSP `frame-ancestors`, so Chrome showed "refused to connect".
  Reproduced in the browser against `HEAD`: *"Refused to display 'https://substack.com/' in a
  frame because it set 'X-Frame-Options' to 'deny'."*
- Links already marked `target="_blank"` (7 of 42 in the sample Not Boring email) were
  silently dropped, because the sandbox lacked `allow-popups`.

## Fix

- **`view.html` + `templates/view.html`**: sandbox is now
  `allow-same-origin allow-popups allow-popups-to-escape-sandbox`, with a comment explaining
  each token and why `allow-scripts` must never be added.
- **`app.js` + `templates/app.js`** (kept byte-identical): new `EmailLinks` module.
  - `retarget(doc)` gives every `a[href]` / `area[href]` an explicit target: `http(s)` links
    to another page get `_blank` + `rel="noopener noreferrer"`; everything else
    (in-page anchors, `mailto:`, `javascript:`, `data:` …) is pinned to `_self`. That
    overrides an email's own `target` and any `<base target>`. The scheme allowlist stops a
    `javascript:` link from opening in an unsandboxed tab.
  - `whenParsed(iframe, fn)` runs as soon as the email's document is parsed (rAF poll), not
    on `load`, which waits for every remote image. `load` is the fallback and ends polling.
  - Hooked in `initViewer()` before `iframe.src` is set. Exposed on `App` for tests.
- **`scripts/build_site.py`**: updated the stale `_anchor` docstring (said the sandbox
  blocked popups). No output change, so no rebuild was needed.

No build-time rewrite: the 17k LFS email files are untouched, and the generated Quincy
pages get the same behaviour at runtime.

## Tests

- New `scripts/test_email_links.mjs` (19 tests, `node --test scripts/*.mjs`): retargeting
  rules, overriding existing targets, rel merging, `<base href>` handling, in-page anchors,
  hostile schemes (`javascript:` in several spellings, `data:`, `vbscript:`, `blob:`),
  unparseable hrefs, idempotency, `whenParsed` timing (about:blank, still parsing, once only,
  load fallback, polling stops), and a guard on the sandbox tokens in both `view.html` copies.
- Mutation check: dropping the scheme allowlist makes the hostile-scheme test fail.
- Node 36/36 pass, Python 61/61 pass.

## Browser verification (Playwright, Chromium)

Real emails pulled through the LFS batch API into a scratchpad copy of the site (this
checkout has LFS pointers only), publisher stubbed with `X-Frame-Options: DENY`:

| | before (HEAD) | after |
|---|---|---|
| headline click | frame refused, no tab | new tab, publisher page scripts run |
| links retargeted | 7/42 had `_blank` (all dropped) | 42/42 |
| iframe after click | navigated away / blocked | still on the email |
| clicked before images finish loading | — | works (`readyState: interactive`) |

Also checked: `javascript:` links (explicit `_blank` and via `<base target="_blank">`)
open no tab and run no script; a `#bottom` anchor scrolls within the frame; a link marked
`target="_top"` opens in a new tab; popup has `window.opener === null` and no referrer;
generated Quincy pages get `_blank` too. No console errors.
